# 09-工程注意事项

本文件记录项目长期积累的「避坑知识」：来自三巨头调研（`doc/调研/`）的教训与本项目自身踩过的坑。与 `doc/03-架构设计.md`（红线，不可违反）和 `doc/08-契约与测试纪律.md`（必须成立、可测试）不同，本文件是软性经验——每条都解释"为什么危险"，供设计、评审、编码时参考，可持续增补。条目编号稳定，删除需注明原因（避免"经验被悄悄遗忘"）。

## 1. 并发纪律

- 以 rayon 数据并行为主，禁止手工 `std::thread` 管理共享可变状态。
- 杜绝全局可变状态（static mut / 全局配置）；一切运行时状态经 `TrainingContext` 显式传递（红线 4）。
- 教训来源：LightGBM OpenMP 全局线程数副作用（#4705/#5102 双 issue）、XGBoost 手写并行 data race 慢性病。

## 2. 性能回归需要门禁，否则不可见

- 优化与正确性耦合的改动（如 SIMD、缓存分块）必须过基准门禁。
- 教训来源：三家性能回归族都缺门禁；LightGBM 提交量中几乎无性能回归修复——不代表没有，只是看不见。

## 3. sketch / 分箱参数固化，不反复调

- quantile sketch 的内存估计、safety factor 等参数一旦验证确定就固化，禁止跟随 issue 反复微调。
- 教训来源：XGBoost 分布式 sketch 多次调整 safety factor（`45861e715` 等），说明参数未沉淀为契约。

## 4. 类别特征是新兴 bug 温床

- OOV（训练未见类别）、UTF-8、nullable 类别、高基数四类边界必须显式测试。
- 教训来源：XGBoost 2025 默认启用类别特征后 OOV/UTF-8/nullable 密集暴露；三家类别特征族持续修复。

## 5. 缺失值/NaN 边界多为静默错误

- 缺失值语义错误往往不崩溃、不报错，只产生错误结果——测试必须显式断言结果而非只看"没崩"。
- 教训来源：LightGBM NaN 输入导致 UB（`0012fc28`）、NaN bin 最高频时出错（`414c7b44`）。

## 6. 加权/量化路径中间量用双精度

- 加权分位数、回归目标统计量等聚合路径，中间量保持 f64，仅在最终输出降精度。
- 教训来源：LightGBM 加权分位数两年内错两次（#5848/#7224），属静默精度错误。

## 7. 绑定层不反哺架构

- 核心库纯 Rust + 可选薄 C ABI；任何语言绑定（Python 等）都是附属品，禁止为其改动核心 API 形状。
- 教训来源：三巨头绑定层修复量 ≈ 核心 C++ 修复量；LightGBM API 兼容修复占比 31%。

## 8. 依赖克制

- 不进跟随上游发版节奏的依赖（GPU 计算栈、底层容器库）；选依赖时问"它是否按月强迫我升级"。
- 教训来源：XGBoost 被 CCCL/cuDF 月更拖累，持续"Fix compilation with latest XXX"。

## 9. 平台矩阵是负担放大器

- MVP 锁 x86_64 Linux/Windows；不预埋平台适配层。需要时再加，且新增平台必须同步 CI 矩阵。
- 教训来源：CatBoost 非主流平台测试事后补齐、问题在用户侧爆发（#2622/#2890）。

## 10. 错误处理显式化

- 解析/反序列化/IO 错误必须显式传播；禁止 `unwrap` 于库代码（CLI 除外）、禁止忽略错误码。
- 教训来源：CatBoost 零拷贝加载未检查 Skip 导致静默损坏（`3d642525ca`）。

## 11. 提交与文档纪律

- "修复"提交与 typo/风格提交分开（三巨头中 catboost 约 1/4 修复是 typo 噪音，严重污染统计与 blame）。
- 本项目文档按 01~09 编号维护；新经验先入本文件，再视情况升级为红线或契约（升级时注明动机）。
