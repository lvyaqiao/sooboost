# 调研：GBDT 三巨头（XGBoost / LightGBM / CatBoost）Bug 分族与代码质量对比

> 调研日期：2026-08-11
> 数据来源：`reference/` 下三个仓库的完整 git 历史（深克隆）
> 目的：为本项目（纯 Rust GBDT）评估「GBDT 领域 bug 的结构性来源」，为架构设计规避历史性坑位

## 0. 三仓概况

| 维度 | XGBoost | LightGBM | CatBoost |
| --- | --- | --- | --- |
| 起始时间 | 2014-02 | 2016-08 | 2017-07 |
| 总提交数 | 7,944 | 3,859 | 50,647 |
| 修复类提交 | 1,459（18.4%） | 1,207（31.3%） | 4,938（9.7%）* |
| 近 1 年修复占比 | 20.3% | 17.4% | 18.9% |
| 开发状态 | 活跃（MT 多线程训练等大功能合并期） | 稳定期（2021 年后提交量逐年下滑） | 稳定期（~110 条/月，2 年 230 活跃作者） |

\* CatBoost 全史 9.7% 被 2023 年内部 monorepo 重导入（19,647 条"Intermediate changes"）和 util/contrib 依赖同步大量稀释；近 2 年实际为 17.1%，其中仅约 40% 真正触及 `catboost/` 本体，且约 1/4 是 typo/style/错误消息类。**真实代码缺陷率三家都在 12~18% 区间，差别不大。**

## 1. 各家 Bug 分族

### 1.1 XGBoost（dmlc，功能最全）

| Bug 族 | 占比 | 结构性风险 |
| --- | --- | --- |
| 构建/CI | ~30% | 17 个 workflow 矩阵庞大，上游工具链漂移频繁打断主线 |
| GPU/CUDA/异构 | ~24% | 依赖 CCCL/RMM/cuDF 按月发版，持续"跟上编译" |
| 分布式/通信 | ~20% | allreduce 内存对齐、CUDA stream、异常路径反复出错 |
| 多线程/并发 | ~16% | 手写并行（sampler/直方图/IO）data race 零星持续 |
| API/接口兼容 | ~14% | sklearn/dask/pandas/polars/arrow 前端每版上游更新引发兼容修复 |
| 平台兼容 | ~7% | 平台×编译器×OpenMP 组合爆炸，WinARM64 是新痛点 |
| 内存/泄漏/越界 | ~7% | 跨语言边界（C API/绑定层）资源生命周期 |
| 量化/分箱(sketch) | ~7% | 分布式 quantile sketch 确定性/内存估计反复调参 |
| 类别特征 | ~4% | 2025 默认启用后 OOV/UTF-8/nullable 编码边界持续暴露 |
| 缺失值处理 | ~3.5% | 缺省语义在 CPU/GPU/类别三套路径的一致性 |
| 数值精度/浮点 | ~1.3% | 占比小但低发生率高风险（locale/denormal/NaN 可复现性） |

热点模块：`src/common`（新基础设施集中地）、`src/tree` 的 sketch/histogram 路径、`collective+data` 跨层交互。**近一年修复量 ≈ R 包 + Python 包修复总量。**
测试：C++ 736 个单测 + 属性测试 + GPU 分布式测试厚实；**缺口：无模糊测试、无覆盖率守护**。CI 有 ASan/UBSan 变体。

### 1.2 LightGBM（微软，训练最快）

| Bug 族 | 占比 | 结构性风险 |
| --- | --- | --- |
| API 兼容 | ~31% | 双重绑定面（Python+R）+ SWIG，sklearn 每版上游更新触发 |
| 构建/CI | ~23% | 170 条 [ci] 修复，工具链依赖持续消耗人力 |
| 文档 | ~13% | 低风险，但推高统计 |
| 分布式/网络 | 7% | 通信协议改动影响面大、难以本地复现 |
| 多线程/并发 | 7% | **OpenMP 嵌套/全局线程数控制反复出问题**（#4705/#5102 双 issue） |
| 平台兼容 | 4.5% | MSVC /permissive- 严格模式与 POSIX 差异 |
| 分箱/直方图 | 3.6% | 与 GPU/稀疏路径交叉，偏移类 bug 静默出错 |
| GPU（CUDA/ROCm/OpenCL） | ~3% | src/cuda 4,947 行独立栈，CPU/GPU 行为需双份一致 |
| 数值精度/浮点 | ~2.7% | 静默精度错误，加权分位数两年内修复 2 次（#5848/#7224） |
| 缺失值/NaN | ~2% | NaN 语义贯穿分箱-分裂-预测全链路，含 UB 类 |
| 类别特征 | 1.9% | 检查逻辑在绑定层重复实现 |
| 内存/泄漏 | 1.9% | 多为绑定层/Arrow 新特性 |

**最脆弱模块：`treelearner` 修复密度 41.6% 全场最高** —— 该目录集中了 6 套分裂器（串行/3 种并行/GPU/linear），逻辑相互复制、组合爆炸。测试：C++ 仅 34 个 gtest + Python 367 个测试函数（主测试面在 Python）；无模糊测试，靠 sanitizer 矩阵兜底。

### 1.3 CatBoost（Yandex，类别特征最强）

| Bug 族 | 占比(近2年样本) | 结构性风险 |
| --- | --- | --- |
| 文档/拼写/错误消息 | ~26% | 内部模板迁移到 GitHub 后持续失配，污染统计 |
| Python API / sklearn 兼容 | ~20% | sklearn tags→sklearn_tags 两代 API、Numpy 2.x、polars 每代变动都转成修复 |
| 构建/CI/发布 | ~13% | 平台×编译器×CUDA 三维矩阵 |
| 平台兼容(Windows/ARM64) | ~7% | 非主流平台测试覆盖不足，问题在用户侧爆发 |
| GPU/CUDA | ~7% | 全史修复率 28% 居首；use-after-free、归约错误、与 CPU 行为不一致（Tweedie 二阶导符号） |
| 未定义行为/内存安全 | ~7% | self-move、未对齐引用、use-after-move，多为 sanitizer 驱动 |
| 多线程/并发 | ~4% | 线程绑定与稀疏特征块耦合，已出现"修了又回滚"（revert 循环） |
| 类别特征/CTR | ~3% | 核心算法区（private/libs/algo），改动影响面最大 |
| 文本/嵌入特征 | ~4% | 新功能迭代快、与 GPU 特征估计器契约易失配 |
| 模型序列化/IO | ~3% | 零拷贝加载路径错误静默传播为模型损坏 |
| 数值精度/量化 | ~2% | 全史 quantization 修复率仅 4.5%，**核心算法区高度稳定** |

测试：109 个 C++ ut 文件（每 lib 一个 ut/）+ canondata 规范输出比对 + Python 分级（small/medium/large）；平台矩阵测试常在事后补齐。

## 2. 三家共通的 Bug 温床（跨项目结构性规律）

把三家的族归并后，**GBDT 领域的 bug 结构性问题高度一致**：

1. **多线程/并发**：三家全中。OpenMP 全局副作用、手写并行的 data race——GBDT 训练天然高并发（分箱/直方图/分裂并行）。
2. **GPU 双轨维护**：三家全有独立 GPU 栈（LightGBM 4,947 行、catboost 修复率 28%）。同一算法在 CPU/GPU 复制实现 → 行为不一致 + 双倍测试面。
3. **语言绑定层**：绑定修复量 ≈ 甚至 > 核心 C++ 修复量。每个绑定（Python/R/Java/Spark）都是独立的 bug 面。
4. **平台×编译器矩阵**：Windows/MSVC 严格模式、macOS、ARM64、ppc64le——纯维护负担，无算法价值。
5. **数值精度**：三家都是"低占比但高风险"——静默错误（结果错但不崩溃），依赖用户 issue 反哺。
6. **缺失值/NaN 语义**：贯穿分箱→分裂→预测全链路的一致性，出问题多为 UB/静默错误。
7. **类别特征**：边界情况（OOV/UTF-8/nullable/高基数）是新兴温床。
8. **文档/typo**：三家都大量存在，显著推高"修复"统计。

**共同结论：核心训练算法本身已经非常稳定，压力全在边界层——并发、GPU、绑定、平台、CI。**

## 3. 维护压力对比

| 维度 | XGBoost | LightGBM | CatBoost |
| --- | --- | --- | --- |
| 绝对维护量 | 中（8k 提交，活跃开发） | 低（3.9k 提交，进入稳定期） | **最高**（50k 提交、6+ 语言绑定、2 年 230 作者） |
| 结构债最重处 | 多后端×多前端组合爆炸 + 上游依赖跟随 | **treelearner 6 套分裂器复制**（修复密度 41.6%） | monorepo 双轨同步 + 生态兼容债务 |
| 趋势 | 修复占比上升（大功能合并期） | 修复占比下降（开发停滞） | 稳定在 ~18% |
| 隐性债 | 分布式 sketch 确定性、浮点可复现性 | 无性能基准门禁、加权分位数精度 | 平台测试事后补齐、GPU 双轨正确性 |

**综合判断**：
- **绝对维护压力：CatBoost > XGBoost > LightGBM**。CatBoost 体量最大、绑定语言最多、内部/开源双轨同步是结构性损耗；XGBoost 正处活跃大功能期，压力为"演化型"；LightGBM 最轻，但它是靠"开发停滞"换来的轻。
- **结构性压力密度（单位代码量）：LightGBM 最高**。它的 6 套 treelearner 复制是典型的"复制粘贴式架构"，一处 bug 修复需多点同步，41.6% 修复密度就是代价。
- 三家真正吃人的不是"梯度提升算法本身"，而是：**并发、GPU 双轨、绑定层、平台矩阵**。

## 4. 对本项目的启示

1. **核心算法不冒险，边界层才冒险**：三家证明 GBDT 核心（分箱/分裂/boosting）成熟稳定，风险在边界。纯 Rust + arrow 零拷贝路线恰好避开了最大的压力源（语言绑定层）。
2. **绝不复制实现**：LightGBM 6 套 treelearner 是反面教材。Rust 泛型/特质（Monomorphized）天生适合单一内核多后端，这正是「想做的.md」里插件化 Loss 的价值。
3. **缺失值/NaN 语义从第一天统一设计**：三家都在这条链路上反复踩坑，且多为静默错误。应在数据层（arrow 原生 null 语义）一次性定义清楚。
4. **多线程是必修课**：三家并发 bug 是慢性病。Rust 的 Send/Sync + rayon 纪律性优于 OpenMP 全局副作用，但 data race 仍需 sanitizer（TSan）守护。
5. **数值精度测试前置**：低占比高风险的静默错误，需要确定性/可复现性测试 + 属性测试（xgboost 已有先例）。
6. **fuzz + sanitizer 从第一天接入**：三家中没有一家有像样的模糊测试，这是新项目的差异化机会（对内存安全尤其有价值）。
7. **平台矩阵是负担放大器**：MVP 阶段应锁单平台（x86_64 Linux），后续再扩；不要重蹈 catboost"平台测试事后补齐"的覆辙。

## 附：原始统计口径说明

- 修复占比 = 提交标题含 fix/fixup/bugfix/bug/issue/hotfix 等关键词（族间有重叠，为近似值）
- CatBoost 2023 年 19,647 条提交为内部 Arcadia monorepo 历史重导入，非真实开发量，趋势分析已剔除
- 三仓均无模糊测试目标；XGBoost 与 LightGBM 无覆盖率工具配置入库
