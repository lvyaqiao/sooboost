# 08-契约与测试纪律

本文件记录本项目对外与对内必须成立的「契约」（可测试的具体不变量，红线 1~7 的操作化落地）与「测试纪律」（每次变更必须对照的 checklist）。红线在 `doc/03-架构设计.md` 定义"为什么"，本文件定义"必须成立什么、如何验证"。内容随项目演进持续增补；新增契约必须可测试，否则不写入本文件。

## 一、契约

### 1.1 数据契约（红线 1、2 落地）

- arrow `RecordBatch` 是唯一数据入参形态；Parquet/Polars/DuckDB 数据必须能零拷贝进入，禁止中间拷贝副本。
- 缺失值语义唯一定义：arrow null 位图 = 缺失；NaN 是否视为缺失由训练配置决定，一旦确定全库一致，任何模块不得自行解释。
- 类别列必须以 `DictionaryArray` 进入；OOV（训练未见类别）、UTF-8、nullable 类别三条边界行为必须显式定义（见 09 注意事项 5）。
- schema 校验：列名/类型/类别映射不一致时**必须显式报错**，禁止静默降级。

### 1.2 模型格式契约（红线 5 落地）

- 模型文件以版本头开头；结构为：版本头 + 模型头 + 树数组 + bin 表 + loss 配置 + 元数据。
- 格式演进必须显式升版本；禁止"读老版本时静默猜"。
- 序列化/反序列化错误必须显式传播（Result），禁止忽略或截断（对治 CatBoost 零拷贝加载静默损坏）。
- 热替换（Arc 原子 swap）的模型必须自包含（含 bin 表），加载即校验完整。

### 1.3 内部不变量（红线 3 落地）

- 相同输入 + 相同种子 → 模型与预测逐位一致（与线程数无关）。
- 并行聚合顺序确定（排序后归约），浮点中间量规则见 09 注意事项 7。
- 该不变量必须写成确定性测试入 CI，任何精度改动须先跑过它。

### 1.4 C ABI 契约（远期，预留位）

- 将来暴露 C ABI 时：符号命名空间稳定、错误码语义固定、资源生命周期（create/free 配对）契约先行定义；绑定层不得反过来影响核心架构（红线之外的软性约定，详见 09 注意事项 9）。

## 二、测试纪律

### 2.1 五类测试入 CI（红线 6 的操作化）

| 类别 | 工具 | 守护什么 | 何时必须新增 |
| --- | --- | --- | --- |
| 确定性测试 | 逐位比对 | 红线 3 可复现性 | 任何精度/并行改动 |
| 属性测试 | proptest | 不变量（如排序稳定性、bin 单调性、sketch 有界） | 新算法、新数据结构 |
| 快照回归 | canondata 思路 | 模型序列化/解析兼容 | 格式变更、序列化改动 |
| fuzz | cargo-fuzz | 解析/反序列化/边界输入不崩溃 | 任何读入外部字节的路径 |
| 基准门禁 | bench CI | 训练/推理性能不回归 | 优化与正确性耦合的改动 |

### 2.2 测试层级约定

- 单测：模块级单元行为（ut 目录镜像 src）。
- 属性测试：不可手写穷举的通用不变量。
- fuzz：输入是外部字节流的地方（模型加载、arrow 读取、bin 表解析）。
- 集成：训练→预测→序列化→再预测的端到端回路。
- 基准：训练时间、推理吞吐，纳入 CI 门禁而非本地自测。

### 2.3 变更 checklist（每次改动对照）

- [ ] 新增功能是否同步了测试面（前瞻式，不是 bug 后补）？
- [ ] 是否涉及精度/并行/顺序 → 确定性测试跑了吗？
- [ ] 是否涉及读入外部字节 → fuzz target 补了吗？
- [ ] 是否涉及模型格式 → 版本头升了吗？快照回归过了吗？
- [ ] 是否涉及性能敏感路径 → 基准门禁过了吗？
- [ ] 是否引入了新的 unsafe → 红线 7 审查注释写了吗？
- [ ] 是否动了全局状态 → 红线 4 违例检查？
